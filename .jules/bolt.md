## 2025-05-12 - [DayOfYear_To_MonthAndDay Loop Elimination]
**Learning:** `SolarGeometry.DayOfYear_To_MonthAndDay` is called intensively within inner loops across thousands of items (e.g., in Raytracing and ThermalSystem where O(N) lookup occurs within O(8760) loops). The default implementation iterated an array sequentially up to 12 times to find the month, wasting massive CPU cycles across large simulations. Also `Math.Floor(hour / 24d)` added unnecessary double casting and floating point operations when `hour / 24` accomplishes the same integer division safely.
**Action:** Replace iterative time calculations with precomputed O(1) arrays (`DayToMonth[365]`) and replace `Math.Floor(double)` with integer division `int / int` anywhere heavily looped logic happens. When handling potentially negative values, ensure true modulo behavior in C# by doing `((val % max) + max) % max`.

## 2025-05-13 - [Multidimensional Array Cache Locality in UTCI]
**Learning:** In C#, 2D arrays `double[,]` are stored in row-major order. Iterating `[probe, hour]` when the array is `[hour, probe]` causes a cache miss on nearly every access for large probe sets, as each access jumps across memory. Swapping the loop order to `[hour, probe]` (Parallel by hour) ensures contiguous memory access, resulting in a ~3-5x performance gain for large simulations.
**Action:** Always align nested loops with the memory layout of the data structure. For `[8760, N]` arrays, parallelize by the first dimension (hour) and iterate the second dimension (probe) in the inner loop to maximize cache-line hits. Renaming progress variables (e.g., `processedProbes` to `processedHours`) ensures the reporting logic matches the new parallelization grain.

## 2025-05-14 - [Annual MRT Calculation Hoisting]
**Learning:** In `EddyLib/OutdoorComfort/MRT.TwoPhaseDDS.cs`, the `SolarGain.ERF` method was called inside a nested loop [8760, N_probes]. This method performed redundant `Get_fp` table lookups and `Math.Sin` calculations for every probe, even though these values are constant for a given hour. Hoisting these calculations out of the inner loop eliminates O(N_probes) redundant operations per hour, which equates to millions of unnecessary calls in annual simulations.
**Action:** Identify and hoist any calculations that are invariant to the inner loop dimensions (e.g. per-hour solar geometry in per-probe loops). Use specialized methods (e.g. `ERF_Optimized`) to pass precomputed values into the hot path to avoid re-evaluating the same logic millions of times.

## 2025-05-15 - [Temporal Wind Factor Cache Locality and Transposition]
**Learning:** In `WindFactorsTemporal.CalcWindFactorsTemporal`, iterating over 8760 hours inside a per-sensor parallel loop caused massive cache misses due to the large stride of the `ValuesTemporalAtProbingHeight[hour, sensor]` array. Additionally, the `WFSpatial[sensor, direction]` input array had poor locality in the inner loop.
**Action:** Parallelize the temporal loop by hour and iterate sensors in the inner loop. To ensure the inner loop remains efficient, transpose the `WFSpatial` input once before the main loop to `[direction, sensor]`. This ensures both read and write operations in the hot path are sequential, leading to significant performance gains (~30%+) for large probe sets.

## 2026-06-12 - [Cache Locality in 2D Array Reductions]
**Learning:** In `UTCI.Equation.cs`, functions like `CalcConditionOfPerson` and `CalcAnnualComfortableHours` operated on large `[8760, N]` arrays using column-major iteration (parallel by probe, inner loop by hour). Since C# 2D arrays are row-major, this caused a cache miss on every access. Swapping the loop order to row-major (outer: hour, inner: probe) ensures sequential memory access. For simple reductions like counting comfortable hours, a sequential row-major pass is significantly faster than a parallel column-major pass due to the elimination of cache thrashing and thread management overhead.
**Action:** Always prioritize row-major iteration (`[i, j]` with `j` in the inner loop) for 2D arrays in C#. Parallelize the first dimension (row) rather than the second to maintain cache-line efficiency.

## 2026-05-30 - [Binary I/O Batching and Multidimensional Array Access]
**Learning:** `RadianceFiles` performed binary I/O by calling `BinaryReader.ReadSingle()` and `BinaryWriter.Write(float)` millions of times in loops, incurring significant stream overhead. Additionally, 2D array population used a single loop with division (`/`) and modulo (`%`) for indexing, which is computationally expensive and hides the contiguous memory layout of C# multidimensional arrays (`[,]`).
**Action:** Use `BinaryReader.ReadBytes` for block reads and `MemoryMarshal.AsBytes` with `BinaryWriter.Write` for buffered writes to minimize call overhead. Replace division/modulo indexing with nested loops to align with row-major memory storage and eliminate redundant arithmetic.

## 2026-05-31 - [Parallel Grain and Transposition Write-Efficiency]
**Learning:** In `WindFactors.VectorLengths`, parallelizing over the smaller dimension (wind directions, typically 8-36) while keeping the larger dimension (sensors, typically 10,000+) in the inner loop is a performance anti-pattern. It causes poor thread utilization and forces non-contiguous memory access on the row-major `double[,]` arrays. Additionally, when transposing arrays as in `WindFactorsTemporal`, ensuring sequential writes to the destination array is more critical than sequential reads from the source due to CPU write-combining buffers.
**Action:** Always parallelize the largest available dimension that maintains row-major contiguous access. When transposing, prioritize sequential writes (`dest[i, j] = source[j, i]` with `j` as the inner loop) to maximize throughput.
## 2024-06-08 - Rhino mesh dimension overhead
**Learning:** Iterating through Rhino geometry components like `mesh.Vertices` manually inside C# incurs major performance penalties due to interop overhead between .NET and native Rhino. Using built-in Rhino functions like `mesh.GetBoundingBox(true)` pushes the loop into native C++, performing orders of magnitude faster.
**Action:** For geometry operations, avoid manual O(N) vertex/face loops in C#; instead, rely on bulk native Rhino operations (e.g. `GetBoundingBox`, `Append`) wherever possible.

## 2024-06-12 - Rhino mesh bulk append optimization
**Learning:** Iterating through Grasshopper/Rhino meshes to append them one-by-one (e.g. `foreach(var obj in geometry) mesh.Append(obj)`) forces Rhino to reallocate its internal unmanaged arrays repeatedly. Caching them into a `List<Mesh>` and using the bulk `mesh.Append(IEnumerable<Mesh>)` method is significantly faster because it calculates the final needed size upfront.
**Action:** When merging multiple `Mesh` objects, replace iterative `.Append(obj)` calls inside loops with a single bulk `.Append(IEnumerable<Mesh>)` call at the end of the collection process.
